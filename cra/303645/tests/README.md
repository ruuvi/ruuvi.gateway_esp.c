# CRA Automated Functional Tests

This directory contains Python automation for selected ETSI EN 303 645 / ETSI TS 103 701 security
tests against a dedicated Ruuvi Gateway. It also contains deterministic host-side tests that verify
the automation itself without contacting hardware.

Python 3.8 is required to match the firmware project's supported build and test environment.
Contributor and AI-agent instructions for this entire subtree are in [`AGENTS.md`](AGENTS.md).

## Structure

| Path | Purpose |
|---|---|
| `test_<id>.py` | Live-DUT functional-test executable for one CRA test case |
| `test_test_<id>.py` | Deterministic host-side tests of the matching automation script |
| `test_lib.py` | Unit tests for shared code under `lib/` |
| `lib/` | Shared configuration, evidence, models, HTTP inventory, and gateway client code |
| `.env` | Local DUT identity and address; never needed by host-side tests |
| `logs/` | Timestamped evidence generated by live tests and execution-level host tests |
| `requirements.txt` | Python runtime and coverage dependencies |

The repeated `test_test_` prefix is deliberate. The first `test_` marks a Python test module; the
remaining name identifies the live automation script under test. For example,
`test_test_5_1_1_2_b.py` verifies `test_5_1_1_2_b.py`.

Shared-library behavior is tested only in `test_lib.py`. The `test_test_*.py` modules may use the
library as infrastructure while testing a functional runner's sequencing, assertions, recovery,
evidence integration, and exit-code behavior.

## Environment setup

Create a Python 3.8 virtual environment from the repository root:

```bash
cd cra/303645/tests
python3.8 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install --requirement requirements.txt
```

The dependencies provide `requests`, PyCryptodome for P-256 ECDH operations, and `coverage.py`.

## DUT configuration

Live tests read `.env` from the current test directory. It must contain exactly these fields:

```dotenv
gw_id=00:11:22:33:44:55:66:77
gw_mac=AA:BB:CC:DD:EE:FF
gw_hostname=gateway.local
```

- `gw_id` is eight colon-separated hexadecimal octets.
- `gw_mac` is six colon-separated hexadecimal octets.
- `gw_hostname` is a DNS name, IPv4 address, or IPv6 address without a URL scheme, port, or path.

Replace the example values with the dedicated test gateway values. Blank lines and full-line
comments are accepted. Unknown and duplicate keys are rejected.

Many tests require the gateway to start in its documented factory-default authentication state.
When a test reports `USER ACTION REQUIRED`, follow its factory-reset instruction before retrying.

## Running tests

Run only the shared-library unit tests:

```bash
cd cra/303645/tests
.venv/bin/python -m unittest --verbose test_lib.py
```

Run all deterministic tests of the functional-test automation:

```bash
.venv/bin/python -m unittest discover \
  --verbose \
  --start-directory . \
  --pattern "test_test_*.py"
```

Run one automation test module:

```bash
.venv/bin/python -m unittest --verbose test_test_5_1_1_2_b.py
```

These commands require no DUT and make no real network requests. The tests use fake HTTP sessions,
responses, clocks, and random sources.

Run a live-DUT functional test separately:

```bash
.venv/bin/python test_5_1_1_2_b.py
```

Live scripts take their configuration from `.env`, communicate with the configured gateway, print
progress, and create a log under `logs/`. Do not run live scripts through `unittest` discovery.

The common process result convention is:

| Exit code | Meaning |
|---:|---|
| `0` | Test passed |
| `1` | A security or functional assertion failed |
| `2` | Setup, transport, protocol, or recovery error prevented a valid verdict |

## Library coverage

Coverage is intentionally calculated from `test_lib.py` alone. This keeps the metric honest: a
functional runner importing or incidentally executing library code cannot hide missing library unit
tests.

```bash
cd cra/303645/tests
.venv/bin/python -m coverage erase
.venv/bin/python -m coverage run \
  --branch \
  --source=lib \
  -m unittest test_lib.py
.venv/bin/python -m coverage report --show-missing --fail-under=95
```

The last command exits nonzero below 95% total branch-aware coverage. For line-by-line inspection,
run `.venv/bin/python -m coverage html` and open `htmlcov/index.html`.

## Continuous integration

[`../../.github/workflows/cra-python-tests.yml`](../../../.github/workflows/cra-python-tests.yml)
runs on relevant pushes and pull requests and can also be started manually. It:

1. Sets up Python 3.8 on Ubuntu 22.04.
2. Installs `requirements.txt`.
3. Runs `test_lib.py` with branch coverage and enforces the 95% threshold.
4. Discovers and runs every `test_test_*.py` module.

The live-DUT scripts are excluded from CI because GitHub-hosted runners do not have access to the
dedicated gateway or its test network.

## Adding or changing a functional test

1. Add or update `test_<id>.py` for the live-DUT behavior.
2. Add or update `test_test_<id>.py` with deterministic fakes that verify the runner's sequence,
   outcomes, cleanup, recovery, evidence, and exit codes.
3. Put reusable configuration, protocol, HTTP, logging, or model behavior in `lib/` and test it in
   `test_lib.py`.
4. Keep DUT access out of host-side tests. Inject sessions, random bytes, clocks, and other external
   boundaries.
5. Run the library coverage command and the complete `test_test_*.py` discovery command before
   submitting the change.

Host-side tests are implementation verification. They do not constitute ETSI compliance evidence;
only an actual live-DUT execution can produce that evidence.
