`load_dut_config(Path(".env"))`, authenticate as `Admin`/`gw_id` through `GatewayClient`, and read

authentication checks. Compare the public representation directly by type and value; do not derive
defaults from saved secrets, duplicate default constants, or change the DUT to manufacture its

Because standalone recovery erases the complete configuration, this unit checks every field in
the default reference before provisioning, including Ethernet, coordinates, scan, NTP and update
settings. Only device metadata (`fw_ver`, `nrf52_fw_ver`, `gw_mac`) and MAC-derived `mqtt_prefix`
and `mqtt_client_id` are excluded from placeholder-default comparison. Identity is independently
verified, then MQTT defaults are checked with the verified DUT MAC substituted for the reference
placeholder MAC. Customized MQTT values are rejected before mutation too. Stable device-derived
values are retained in the complete restoration baseline.

A non-200 default login must mark the shared `FACTORY_RESET_MESSAGE` before raising setup ERROR.
Catch Basic/Digest `GatewayAuthenticationModeError` even when interactive login raises before
returning. Retain recovery advice in both `RunResult.recovery_message` and terminal/evidence output.
Once configuration is available, validate any exposed MAC before default fields: a wrong or
malformed identity is ERROR without reset advice. If MAC is absent, a non-default baseline is ERROR
without reset advice for an unverified device. Missing, wrongly typed, or non-default required
fields stop the run before probes or mutations; only a verified identity permits baseline reset
advice.

Use the shared reset instruction: back up needed settings; local configuration, credentials, tokens,
and uploaded certificates/private keys are erased and connectivity is interrupted, while cloud
accounts and forwarded data remain. Hold CONFIGURE through the initial restart until repeating red
200 ms on/200 ms off signals boot-time erase completion, then release. Release triggers another
restart, after which the configuration hotspot opens. About eleven seconds is observed elapsed time,
not a fixed threshold; the five-second restart timer alone does not prove erasure.

Every configuration read, including post-provisioning, bearer, certificate-presence,
preservation and recovery reads, must confirm the same valid nRF52 identity. Missing,
malformed or different identity stops further writes and factory-reset prompts immediately;
identity failures are never retried as transient network failures.

## Objective

Create a functional live-DUT test with automated API checks and operator-confirmed network
transitions for **ETSI EN 303 645 / ETSI TS 103 701 test case 5.11-1-2, Test Unit A: Typical User
Data Creation**.

This unit is the **data-creation setup** stage of the user-data-erasure test group. It must run
against a physical Ruuvi Gateway and provision **every category** of non-default personal/user data
that the source requires (Wi-Fi station credentials, Web-UI admin password, M2M API keys, custom
HTTP/MQTT telemetry targets with their secrets, remote-config assets, and user SSL/mTLS
certificates), verify that each category is actually committed to device storage, and emit a
machine-readable **evidence manifest** describing each created item and how commitment was proven.
The standalone runner recovers the baseline, so this manifest is historical; a later
erasure-verification unit (5.11-1-2 Unit C) must establish and verify its own current seed.

Because this is the _creation_ stage — not the erasure stage — it must also be safe to run
standalone: when run on its own it must restore the DUT to its factory/baseline configuration at the
end, so it does not leave a dedicated bench in a custom-provisioned state. Reconcile the two roles
explicitly (see "Standalone vs pipeline mode").

### Operator-assisted workflow

1. The runner authenticates over LAN, verifies the nRF52 MAC and captures two stable default
   configuration reads. Hotspot requests bypass authentication; starting at `10.10.0.1` or following
   a captive-portal redirect cannot verify passwords or API keys.
2. When prompted, briefly press and release CONFIGURE (well before five seconds), then join
   **Configure Ruuvi Gateway XXXX** on the **host running the script**. The prompt derives the
   suffix from the configured nRF52 identity. Wait for DHCP and press **Enter**. The script then
   contacts the Gateway API at `http://10.10.0.1` and independently verifies identity.
3. The runner sends the configured Wi-Fi credentials via hotspot-only `/connect.json` and waits up
   to 30 seconds for readback. A fresh successful station status, matching SSID and valid station IP
   provide indirect password-use evidence; saved-SSID readback verifies commitment. Accepted
   provisioning alone is insufficient. It then selects Ethernet, calls `/connect.json` with null
   SSID/password, and finishes configuration through `POST /ruuvi.json` to close the hotspot. This
   does not erase the saved station credentials.
4. When prompted, reconnect the host to normal LAN and press **Enter**. Keep Gateway Ethernet
   connected and close Gateway browser pages. The runner retries authenticated LAN access for up to
   90 seconds, plus an in-flight HTTP timeout, before continuing the creation checks.
5. After mutations, recovery prompts for a **physical factory reset**, replacing API cleanup. Hold
   CONFIGURE through the initial restart until red repeats **200 ms on / 200 ms off**, then release.
   Release causes a second restart. About eleven seconds is typical elapsed time, not a completion
   threshold. Join the named hotspot, wait for DHCP, then confirm only after observing the
   completion signal. The runner verifies identity and the complete captured baseline, reconnects
   Ethernet and prompts for the host's return to LAN. It verifies default authentication, the
   baseline hash, and rejection of the created admin password and API keys.

Enter confirms each action. `q` followed by Enter stops normal checks and attempts recovery;
recovery can itself need confirmation. EOF or Ctrl+C at a prompt never confirms an action. Declined,
incomplete or unverified recovery produces ERROR with evidence/manifest paths. No reset is offered
for a known identity mismatch. If no mutation or network transition was attempted, the runner
verifies the unchanged baseline without requesting a reset. The runner does not drive a Pi
controller, change the host network, or press buttons itself.

### Commitment checks and limits

The local HTTP fixture accepts telemetry POSTs and serves a remote-config `.json` document. No
separate `python -m http.server` is needed. Both endpoints require exact generated Basic
credentials. `/validate_url` uses `use_saved_password=true` with no replacement password; wrong-user
rejection and correct-user success must match application statuses 401 and 200. Local server
counters must also show rejected and accepted requests. HTTP 200 alone is not proof. The remote
document is `{"remote_cfg_use":true}`; `use_remote_cfg` is an internal C field name, not the
accepted JSON key. Validation parses the document without applying it, while stored
`remote_cfg_use=false` keeps scheduled remote configuration disabled.

The RO key is verified in a separate bearer session. The RW write explicitly sends the current
`mqtt_prefix`, `mqtt_client_id` and `mqtt_data_format` from the immediately preceding read as a
workaround for [firmware issue #1650](https://github.com/ruuvi/ruuvi.gateway_esp.c/issues/1650). The
**complete** configuration comparison and before/after hashes remain; any unexpected change still
produces FAIL. Console and manifest identify the workaround. This does not verify empty-object POST
behavior or establish that the firmware bug is fixed.

Ten generated certificate/private-key files are checked separately. If `/extra_cfg` cannot read
NVS-backed files, the runner uses `storage.<filename>` presence flags, records indirect proof, and
does not invent readback hashes. TLS enable flags are not file-presence evidence. Plain HTTP and
public-broker checks do not establish HTTPS/mTLS handshake correctness.

Track every attempted upload for recovery, but require presence only after an accepted upload.
For a rejected upload or lost response, independently observe its boolean storage presence flag
when checking preservation. An unchanged rejected upload must not block the RW no-op probe.
An unavailable or malformed flag leaves the upload's storage outcome unresolved: preservation
is ERROR and the RW write is not run. Upload rejection or transport loss remains a certificate
category ERROR even when observed storage and the RW probe pass.

The manifest `logs/test_5_11_1_2_a_manifest_<UTC>.json` records the full baseline/hash, intended
items, commitment methods and per-check outcomes. It is checkpointed before mutation and reset, then
atomically finalized after recovery. For compatibility the recovery record is named `restored`; the
console outcome is **factory reset**. A recovered manifest is historical evidence, **not a currently
seeded-device hand-off or forensic erasure proof**. Unit C must establish a fresh verified seed
independently.

PASS requires every category committed, verified baseline recovery and a written manifest. Missing
setup or proof produces ERROR; a proven configuration inconsistency produces FAIL. Earlier failures
remain recorded even if recovery succeeds. Offline tests and successful reset alone cannot establish
a live compliance PASS.

## Standalone vs pipeline mode (reconciling the two roles)

Because `.env` carries no mode flag and no CLI args are allowed, the script always behaves the same
way and is deterministic:

- It always creates the data, verifies commitment, and writes the manifest (the pipeline hand-off).
- In the mandatory `finally` path, offer **operator-confirmed factory reset** after mutations or
  interrupted network transitions. Keep the existing historical `restored` manifest record for
  compatibility, but label the console outcome and progress step **factory reset**.
- Checkpoint evidence before the prompt; a checkpoint failure must not prevent recovery.
- Identify the previously verified Gateway by MAC in the prompt. Instruct the operator to hold
  CONFIGURE through the initial restart until red repeats 200 ms on/200 ms off, then release.
