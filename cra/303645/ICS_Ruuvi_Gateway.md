# Implementation Conformance Statement (ICS) — Ruuvi Gateway

This Implementation Conformance Statement (ICS) states the implementation of the provisions of
`ETSI TS 103 645` V3.1.1 (2024-01) / `ETSI EN 303 645` for the `Ruuvi Gateway`, following the
standardized pro forma of **Annex B.1**. The conformance assessment methodology is `ETSI TS 103 701`
V2.1.1; each row of the table below provides a precise, audit-grade technical justification
cross-referencing the corresponding Implementation eXtra Information for Testing (IXIT) documents
and self-assessment test group compliance files.

### Document Metadata

* **Device Under Test (DUT)**: Ruuvi Gateway
* **Supplier Organization (SO)**: Ruuvi Innovations Oy
* **Assessment Methodology**: `ETSI TS 103 701` V2.1.1
* **Reference Standard**: `ETSI TS 103 645` V3.1.1 (2024-01) / `ETSI EN 303 645`
* **ICS Status**: Audit-Ready, Complete (All documentation gaps resolved)

### ICS Guide & Notation

* **Reference**: Provision number in `ETSI TS 103 645` / `ETSI EN 303 645`.
* **Status**: Verbatim status from Annex B of `ETSI TS 103 645`:
  * **M**: Mandatory requirement.
  * **R**: Recommendation requirement.
  * **C (n)**: Conditional requirement (numbered condition *n*).
  * **F (f)**: Feature-dependent requirement (lettered feature *f*).
* **Support**: Claim of implemented support:
  * **Y**: Supported.
  * **N**: Not supported.
  * **N/A**: Not applicable (due to unmet conditions or absent features).
* **Detail**: Complete, audit-grade technical justification and functional rationale
  cross-referencing the corresponding IXIT and Self-Assessment documents.

#### 5.1 No universal default passwords

| **Provision 5.1-1**  | M F (a)        | **Y**   | Feature (a) applies as password-based authentication is implemented to gate administrative access. The out-of-the-box primary access barrier (`AuthMech-LAN-WebUI-Default`) utilizes a hardware-bound, non-universal cryptographic password layout. All alternative machine-to-machine interfaces (`AuthMech-M2M-API-Bearer-RO/RW`) and advanced custom configurations are disabled, unpopulated, or locked by default until explicitly enabled by an authenticated administrator. This provides a baseline entropy pool of $2^{64}$ and remains entirely unlinked from any discoverable network metadata layer, eliminating the risk of class-wide automated attacks. Cross-reference: **ixit_1-AuthMech** (`AuthMech-LAN-WebUI-Default`) / **ixit_10-SecParam** (`SecParam-Hardware-DeviceID`) / **Self_Assessment_Test_Group_5_1-2.md**.                                        |

Cross-reference: **ixit_1-AuthMech** / **ixit_11-SecComMech** (`SecComMech-LAN-Bearer-Authentication`) / **Self_Assessment_Test_Group_5_1-2A.md**.                                                                                                    |
| **Provision 5.1-3**  | M F (c)        | **Y**   | Feature (c) applies as cryptographic authentication is implemented. Authentication mechanisms (`AuthMech-LAN-WebUI-Default/User-Defined`) enforce best-practice cryptographic primitives (AES-128, SHA-256, and ECDH over NIST P-256 curve) through the native mbedTLS engine. Plaintext passwords are never transmitted on the wire; the custom `x-ruuvi-interactive` pipeline utilizes a nonced MD5 challenge-response scheme bound by an outer `SHA256(challenge:MD5_result)` loop, and all subsequent data modification payloads are encrypted over an isolated ECDH transport layer. Cross-reference: **ixit_1-AuthMech** / **ixit_11-SecComMech** (`SecComMech-WebUI-Session`) / **Self_Assessment_Test_Group_5_1-3.md**. |
| **Provision 5.1-4**  | M F (d)        | **Y**   | Feature (d) applies as user authentication is supported. Modifying these values triggers a persistent NVS flash write that updates the `ruuvi.json` manifest within the `nvs` partition, replacing the active keys and immediately invalidating former session contexts. Clear, step-by-step instructions are published on docs.ruuvi.com. Cross-reference: **ixit_1-AuthMech** (`AuthMech-LAN-WebUI-User-Defined`) / **ixit_2-UserInfo** (Documentation of Change Mechanisms) / **Self_Assessment_Test_Group_5_1-4.md**.                                                                                          |
| **Provision 5.1-5**  | M C (14) F (e) | **Y**   | Condition (14) is met as the device has no resource constraint preventing brute-force defense, and Feature (e) applies as authentication is network-accessible. The device actively mitigates automated online brute-force attacks by combining high-entropy authentication keyspace (64-bit hardware DEVICEID and 256-bit PRNG M2M tokens) with a mandatory, application-layer 1-second delay applied to all login POST requests. This delay effectively throttles programmatic dictionary sweeps, making automated attacks mathematically and operationally impracticable. Cross-reference: **ixit_1-AuthMech** / **Self_Assessment_Test_Group_5_1-5.md**.                                                                    |
